# 自动签到：调研

> 2026-11-03。目标是「给小李加一个自动签到、每天领积分的能力」。
> 这份只写**查到的事实**和**技术判断**，不谈怎么做（做法在 `需求-自动签到.md`）。

## 0. 先说结论

**技术上能做，但这件事和现在小李的定位是冲突的，需要单独做成一个脚本，先验证再谈整合。**

理由三条，后面每条都有细节：

1. **签到确实存在，而且不止一家**：WorkBuddy 有「Buddy 加油站」，TRAE 有每日签到。你记的「每天 100 积分」两家都对得上。
2. **签到入口基本都在客户端或需要登录态的网页里**，没有公开 API，必须带着你的登录凭证去请求。「没有公开 API」是这件事难的根本原因。
3. **小李现在的核心承诺是「单机、离线、不发网络请求」**（上个月为适配包破例开了 GitHub 一个口子，还限定成只有点按钮才联网）。自动签到要**长期存你的凭证** + **每天自动联网**，是相反的事。硬塞进去会把项目最值钱的那个性质弄没。

## 1. 我上一轮查错了什么

上一轮我查了 WorkBuddy 的官方[积分说明](https://www.workbuddy.cn/docs/workbuddy/Credits)，那份文档里只写了「积分按月发放、当月有效、买会员/加量包获得」，**确实没有签到**。

但那只是**计费口径**的文档，不是**活动页**。签到属于运营活动，写在不显眼的地方（客户端左下角一个叫「Buddy 加油站」的入口）。

我当时的判断是「WorkBuddy 里没有签到」，这个结论**是错的**。错在只查了官方计费文档就下结论，没有交叉验证第三方实测。这次补上了。

## 2. 查到了什么

### 2.1 WorkBuddy（腾讯）

来源：今日头条《workbuddy每天自动签到领取100积分，攻略来了！》（2026-08-31）、
知乎《workbuddy免费积分全渠道实测，每月3500分起步，连签到…》（2026-09-02）。

| 项目 | 内容 |
| --- | --- |
| 入口 | **客户端左下角 →「Buddy 加油站」** |
| 每日奖励 | 100 通用积分 |
| 连续奖励 | 连续 7 天额外给 1000 积分 |
| 断签代价 | **不是少 100，是当周那 1000 分拿不到**，要重新连 |

> 注意：这两篇都是**第三方**写的，不是官方文档。具体数字和入口位置可能已经变了，需要你实际打开客户端核对一次。

`Buddy 加油站` 在必应里搜不到独立词条（返回的全是词典结果），说明它是客户端里的界面名称，**没有对应的公开网页入口**。这一点很关键：**它在桌面客户端里，不在网页上**。

### 2.2 TRAE（字节）

来源：TRAE 官方中文社区《每日签到积分》（2026-10-09，官方账号「TRAE宝」回复）。

| 项目 | 内容 |
| --- | --- |
| 每日奖励 | 免费用户 **100** 积分；会员 200 积分 |
| 有效期 | 签到获得的积分 **31 个自然日**过期 |
| 通用性 | 可在 TRAE Code 和 Work 中通用 |
| 规则变动史 | 200(Work专用) → 会员200/免费150 → 会员200/免费100 |

这条的价值在于**它是官方社区账号亲口确认的**，比自媒体可信。而且它顺带暴露了这类活动的通病：**规则会改，而且改得很随意**（半年改了两次，免费用户从 150 砍到 100）。

#### 2.2.1 实测：代码里有签到接口，但活动目前没开（2026-11-04）

用户登录了自己的 TRAE（`TraeCode CN 1.107.1`）后直接说：**「trae 没有积分领取的活动」**。这句话和代码对上了，也和下面查到的实现吻合。

**代码里确实有签到**（`resources/app/out/main.js`，未打包，直接可读）：

```js
fetchCheckinCreditsStatus(){ return this._requestCheckinCredits("/trae/api/v2/ug/checkin_credits/status","POST","checkin_status") }
claimCheckinCredits(){ return this._requestCheckinCredits("/trae/api/v2/ug/checkin_credits/claim","POST","checkin_claim") }
```

**但有三道闸，任何一道不通就调不出去**：

| 闸 | 代码 | 说明 |
| --- | --- | --- |
| 地区/渠道 | `providerCode !== Do.CN` 就抛 | 只有 CN 版走这条路 |
| **账号类型** | `account.scope !== Nt.MARSCODE` 就抛 | **只认 TRAE 自家账号**，火山/字节云账号不行 |
| **服务端开关** | 返回体里有 `data.enable`，类型必须是 boolean | **活动开没开由服务端说了算** |

第三道就是关键。`checkin_status` 的协议校验写得很明白：

```js
typeof c.data?.enable != "boolean" || typeof c.data?.checked_in != "boolean" → 判定协议错误
```

也就是说接口本身**随时在**，只是服务端用 `enable` 字段决定「这个账号现在能不能领」。用户看到「没有积分领取的活动」，就是 `enable: false`。

**另外两个坑**（如果以后活动真开了，接的时候要记着）：

1. **API 域名不是写死的**。请求地址是 `bootService.getApi(ugApi, path)`，而 `ugApi` 来自**运行时下发的 boot 配置**（`getBootConfig()`）。安装包的 `out/config/` 目录根本没发布。实测 `https://api.trae.com.cn` 对该路径返回 404，连乱编的路径也是 404，说明那个域名不承接 ug 接口，**必须从运行中的客户端里取真实 base**。
2. **鉴权头是 `Cloud-IDE-JWT <token>`，不是 `Bearer`**：`mixAuthorization(e,i){ return {...e, Authorization:`Cloud-IDE-JWT ${i}`} }`。另外还要带 `x-device-id`（`_applyUgDeviceHeaders`）。

**凭证也不再是明文文件了**。8 月那次它把 token 明文写在 `~/.trae-cn/trae-jwt-token`（JWT，925 字符，`iss: trae`，有效期 7 天）。这次登录后**那个文件没了**，改成加密存储，渲染进程的 localStorage/sessionStorage 里也扫不到 —— 只能走 CDP 或读主进程。

**结论：TRAE 这一站现在做不了，而且不是因为技术，是因为活动没开。** 等 `enable` 变 true 再说，那时候照 `2.2.1` 这几条接就行，框架已经留好位置了。

### 2.3 其他厂商

- 做签到的是**AI 编程/办公工具**这一类（WorkBuddy、TRAE），因为它们有「积分/额度」这种按次消耗的资源，且有拉日活的诉求。
- 聊天类产品（DeepSeek、Kimi、通义、豆包、智谱等）**没有搜到**明确的「每日签到领积分」活动——它们的免费额度一般是按量给或用完为止。
  这一条是**基于搜索结果的缺失**，不是查证过它们的全部活动页，别当成定论。

**所以「AI 厂家签到活动」这个赛道确实存在，但集中在工具型产品，不在聊天类产品。**

## 3. 技术上难在哪（逐条）

### 3.1 没有**对外公开**的 API（但客户端内部接口已定位）

签到是产品内部的运营功能，厂商没有任何理由对外提供签到 API。

但这不等于「查不到」。WorkBuddy 是 Electron 应用，**前端代码就在本机的 `app.asar` 里**，
拆开就能读到它自己怎么调签到。我已经拆完了，接口在 5.0 节，不需要抓包。

### 3.2 登录态怎么拿（两种方式都要）

| 方式 | 怎么做 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Cookie / Token** | 你从浏览器 F12 或客户端里复制出来，粘给脚本 | 简单、不碰密码 | **会过期**（几天到几周），过期了要重贴 |
| **账号密码** | 脚本自己调用登录接口拿 Token | 一次配置长期有效 | 要处理验证码、设备指纹、短信、二次验证；**风险更高** |

你说了两种都要提供，那两种都得做，但**必须做成一主一备**：Cookie 为主（安全），账号密码为备（省事）。不能默认让人存密码。

### 3.3 WorkBuddy 是桌面客户端（**已解决，见 5.0**）

`Buddy 加油站` 在**客户端左下角**，我一开始担心的是：

- 签到走客户端私有协议 → 网页上没有入口，抓包得抓客户端；
- 抓客户端要 Fiddler / mitmproxy 中间人代理，还得处理证书；
- Electron 客户端常有**请求签名**，那样模拟请求基本没戏。

**拆了 `app.asar` 之后，这三条担心全部不成立**：它就是三个普通 HTTPS JSON 接口，
认证只有 `Authorization: Bearer <token>`，没有签名。详见 5.0。

### 3.4 规则会变

TRAE 半年改了两次签到规则。任何写死的签到逻辑，都可能在某天突然失效。所以脚本必须**失败得响亮**（明确告诉你「今天没签上，原因是 X」），而不是悄悄失败。

### 3.5 定时执行

「每天自动」需要有个东西每天跑一次。三个选择：

| 方案 | 说明 | 代价 |
| --- | --- | --- |
| Windows 计划任务 | 系统级，开机就算你在睡觉也跑 | 要注册任务，可能有权限问题 |
| 小李启动时补签 | 打开小李时如果今天没签就签 | 需要小李每天开一次 |
| 常驻进程 | 一个后台程序一直跑 | 多一个常驻进程，用户可能不喜欢 |

## 4. 风险提示（我不能替你决定的部分）

以下三条我只陈述事实，不替你判断值不值得：

1. **用户协议**：绝大多数产品的用户协议里，自动化脚本操作账号是被禁止的。厂商有权封号或清空积分。WorkBuddy 和 TRAE 的服务条款我没逐条查，你需要自己确认。
2. **凭证安全**：把 Cookie 或密码存在本机文件里，等于账号安全降级到一个明文 JSON。如果那个 JSON 被同步到网盘（小李的备份机制会导出明文 JSON），风险会放大。
3. **风控**：每天固定时刻、固定 IP、无浏览器指纹的请求，容易被识别成脚本。轻则签到失败，重则触发验证或限制。

## 5. 可行性判断

### 5.0 已经查实的结论（2026-11-04）

你确认 WorkBuddy 是客户端之后，我直接拆了它装在本机的 `app.asar`（182 MB），
**把签到这条链路的源码读出来了**。原来担心的「客户端私有协议 / 请求签名」**不存在**。

WorkBuddy 5.9.3 是 **Electron 应用**（`D:\Program Files\WorkBuddy\`，Electron 37.10.3），
签到就是三个**最普通不过的 REST 接口**：

| 用途 | 方法 | 路径 | 请求体 |
| --- | --- | --- | --- |
| 查今天签没签（推荐） | POST | `/billing/meter/checkin-activity-status` | `{}` |
| 查签到状态（备用） | POST | `/billing/meter/checkin-status` | `{}` |
| **执行签到** | POST | `/billing/meter/daily-checkin` | `{}` |

源码里的实际调用（`app.asar` 里 `BackendProvider` 类）：

```js
async getCheckinStatus() {
  const e = await Z.post(`/billing/meter/checkin-status`, {})
  return e?.code === 0 && e?.data ? e.data : null
}
async claimDailyCheckin() {
  const e = await Z.post(`/billing/meter/daily-checkin`, {})
  return e?.code === 0 && e?.data ? e.data : { code: e?.code ?? -1, ... }
}
```

**认证方式只有 `Authorization: Bearer <token>`**，没有请求签名、没有时间戳、没有 nonce。
（源码里 `getCheckinRequestHeaders()` 在基类中是个**空方法**，桌面端没有往里塞任何东西，
全靠 http 客户端自动加那个 Bearer 头。）

**API 基址**（从 `C:\Users\HW\.workbuddy\failover.json` 读到，是运行时配置不是写死的）：

- 主：`https://copilot.tencent.com`
- 备：`https://www.workbuddy.cn`、`https://wb.tencentbuddy.com`

**返回结构**（源码里的字段映射，反序列化后）：

```js
// 查状态 → checkin-activity-status
{
  active, today_checked_in, streak_days, daily_credit, today_credit,
  is_streak_day, next_streak_day, streak_bonus_days, streak_bonus_credit,
  checkin_dates, total_credits, start_time, end_time,
  activity_name, claim_button_text, action_button, ...
}

// 签到成功 → daily-checkin
{ code: 0, credit, streak_days, is_streak_day }
```

`today_checked_in` 就是「今天签没签」的权威字段 —— 正好对应需求文档 4.3 节
「先查真实状态，绝不靠自己记」的设计。

**匿名探测验证**（不带凭证请求了一下）：

| 请求 | 结果 | 说明 |
| --- | --- | --- |
| `/billing/meter/daily-checkin` | `401` | 网关要求鉴权 |
| `/totally/made/up/path/12345` | `404 Route Not Found` | 不存在的路径是 404 |

**注意一个易误判的点**：`/billing/meter/` 这整个前缀在**未鉴权时一律返回 401**，
连我构造的假端点 `/billing/meter/definitely-not-exist-xyz` 也是 401。
所以 401 只能证明「这个前缀存在」，**不能证明具体端点存在**。
端点的真实性依据是**源码里的调用字符串**，不是探测结果。

### 5.1 落到哪一档

| 情形 | 可行性 | 本次结论 |
| --- | --- | --- |
| 普通 REST + Bearer Token + 无签名 | ✅ 高 | ← **WorkBuddy 就是这一档** |
| 带动态签名/时间戳 | ⚠️ 中 | 本次没遇到 |
| 客户端私有协议 | ❌ 低 | 本次没遇到（就是标准 HTTPS JSON） |
| 有验证码/人机校验 | ❌ 极低 | 签到接口**没有**，但不排除后续加 |

**结论：可行，且属于最理想的一档。** 不需要 Fiddler、不需要中间人代理、不需要破签名。
唯一要解决的是「怎么拿到那个 Bearer Token」。

### 5.2 剩下唯一的不确定性：Token 从哪来

签到请求本身已经彻底搞清楚了，现在唯一的未知是**认证**：

- **Cookie/Token 方式**：从客户端或网页版拿到现成的 Token 填进去（Token 会过期，需要重贴）
- **账号密码方式**：找到登录接口自己换 Token（登录接口通常有验证码/滑块，这是难点）

**Token 存在哪**：客户端把它加密存在 `C:\Users\HW\.workbuddy\keyblob`（336 字节）
和 `workbuddy.db` 里，直接解密属于额外逆向，**不建议走这条路**——
让你手动贴 Token 更简单也更容易维护。

### 5.3 实测结果：已经完整跑通（2026-11-04）

写完脚本后当场验证，**一次成功**。

**取 Token 的办法（比预想的简单）**

客户端源码里有这么一段：

```js
if (process.env.WORKBUDDY_REMOTE_DEBUGGING_PORT) {
  electron.app.commandLine.appendSwitch('remote-debugging-port', n)
}
```

这是**官方留的调试开关**。设这个环境变量启动客户端，就开了 CDP 调试端口，
连上去能看到它自己发的所有网络请求，`Authorization` 头直接就在里面。

实测拿到的 Token 是 Keycloak 签发的 JWT：

| 字段 | 值 |
| --- | --- |
| `iss` | `https://www.workbuddy.cn/auth/realms/cop` |
| `sub` | 账号 UID |
| `exp` | 约 30 天后 |
| 长度 | 1566 字符 |

**不需要解密 `keyblob` 了**，那条路可以划掉。

**真实返回（2026-11-04 02:19，签到前）**

```json
{"code":0,"msg":"OK","data":{
  "active":true,"today_checked_in":false,"streak_days":1,
  "daily_credit":100,"today_credit":100,
  "checkin_dates":["2026-11-03"],
  "week_checkin_days":1,
  "week_progress":[false,true,false,false,false,false,false],
  "total_credits":100,
  "start_time":"2026-09-30 00:00:00","end_time":"2026-12-31 23:59:59",
  "theme_name":"Buddy加油站","activity_name":"Buddy应用"}}
```

**签到后**

```json
签到：{"code":0,"data":{"credit":100,"streak_days":2,"is_streak_day":false}}
复核：today_checked_in: true, streak_days: 2, total_credits: 200
```

积分从 100 → 200，连续天数 1 → 2。**每天 100 分这个数字，和之前搜到的第三方文章对得上。**

**顺带发现的两件事**

1. `week_progress` 是一周七天的 true/false 数组（周一起算），可以直接用来画「本周打卡」。
2. `checkin-activity-status` 和 `daily-checkin` 在 `www.workbuddy.cn` 和
   `copilot.tencent.com` 上都能通，返回一致。

**所以结论更新为：可行，且已验证完成。**
